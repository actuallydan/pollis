# Localization (i18n)

How the React renderer gets its user-facing copy, where the language
preference lives, and what a follow-up locale actually has to touch.

Working checklist for adding a locale: [`frontend/src/i18n/README.md`](../../frontend/src/i18n/README.md).
This article is the design record.

## Stack

`i18next` + `react-i18next`, initialized once in `frontend/src/i18n/index.ts`
and mounted as an `I18nextProvider` in `main.tsx`, outside `ErrorBoundary` and
`QueryClientProvider` so even the crash screen can be translated.

| File | Role |
|------|------|
| `frontend/src/i18n/index.ts` | i18next init, `setLanguage`, `adoptUserLanguage`, `<html lang/dir>` sync |
| `frontend/src/i18n/languages.ts` | `SUPPORTED_LANGUAGES`, tag normalization, OS-locale resolution |
| `frontend/src/i18n/namespaces.ts` | The namespace list; `common` is the default |
| `frontend/src/i18n/storage.ts` | Device-local `localStorage` persistence |
| `frontend/src/i18n/resources.ts` | Eager `import.meta.glob` of every catalogue |
| `frontend/src/i18n/locales/<lng>/<ns>.json` | The catalogues |
| `frontend/src/components/Preferences/LanguageSection.tsx` | The picker |

## Shipped locales

| Code | Endonym | `dir` | Notes |
|------|---------|-------|-------|
| `en` | English | ltr | Source catalogue and `fallbackLng`. Every key originates here. |
| `ru` | Русский | ltr | Machine-translated, pending native review. All 38 plural families carry the full Russian `_one`/`_few`/`_many`/`_other` set. |

`en` is the only catalogue a new key may be *authored* in; every other locale
is a translation of it, so "what is still untranslated" stays a diff against
`en` rather than a hunt through the source.

## Namespaces

One JSON file per feature area, not one flat catalogue: a translator working
on voice should never have to read the settings copy.

`common` (shared verbs/nouns), `auth`, `nav`, `chat`, `channels`, `dms`,
`voice`, `settings`, `search`, `emoji`, `saved`, `errors`, `arcade`.

Keys are addressed `namespace:section.item` and are **stable identifiers, never
the English text** — so a copy edit stays a copy edit instead of orphaning
every translation of that string.

## Where the language preference lives, and why

**Device-local `localStorage`**, keyed by user id, mirroring the device-local
font size (`loadDeviceFontSize` in `utils/colorUtils.ts`). It is *not* in the
synced preferences blob.

Two reasons, one of which is decisive:

1. Language is an OS-level property of the machine, like the keyboard layout.
   A shared office machine in one language and a personal laptop in another is
   a real configuration that syncing would break.
2. **Decisive:** the synced blob is read through `get_preferences`, which needs
   a signed-in user *and* an unlocked local DB. The login, PIN-entry and
   enrollment screens have neither. A synced-only preference therefore could
   not localize the first screens a non-English reader ever sees — which is
   most of the point of the feature.

Saving for a signed-in user also writes a device-wide entry, so the next
pre-auth boot speaks the language this machine last chose rather than falling
back to the OS guess. `adoptUserLanguage`, called from `completeSignIn` in
`App.tsx`, re-resolves to the signing-in user's own choice before the shell
renders.

## First-run default

`resolveInitialLanguage()`:

1. the stored device choice, if any;
2. otherwise the first entry of `navigator.languages` we ship a catalogue for
   — under Tauri the webview inherits the OS locale, so this is the OS's
   answer, and under the Playwright browser tier it is whatever the test sets;
3. otherwise English.

Region subtags degrade to the base language (`pt-BR` → `pt` when `pt` ships),
because a user should land on the language they read rather than dropping all
the way to English over a missing regional catalogue.

**Registered codes are base tags — the degrade rule is also a constraint on
what a locale may call itself.** `normalizeLanguage` splits on the first
separator and matches the base, so a `zh-Hans` entry could only ever be
selected by an OS reporting exactly that tag, which no real one does (`zh-CN`,
`zh-Hans-CN` both reduce to `zh`). Casing rules it out from the other side too:
`normalizeLanguage` lowercases every tag, while i18next canonicalizes through
`Intl.getCanonicalLocales` before checking `supportedLngs`, so `zh-hans` fails
i18next's check and `zh-Hans` fails ours — and the failure mode is a silent
fall back to English, not an error. Simplified Chinese therefore ships as `zh`,
with `简体中文` as the endonym carrying the script distinction. Shipping a
second script for one language would mean reworking `normalizeLanguage`, not
adding a subtagged entry.

## Fallback

`fallbackLng: "en"`, `returnEmptyString: false`. A key missing from the active
language, or present but left as `""` in a half-finished catalogue, renders the
**English** string rather than a raw key. Partial translations are always
shippable, and a locale can land incrementally.

## Plurals

Every count-bearing string is a plural key (`foo_one` / `foo_other` in `en`),
**even where English needs only two forms**. Russian, Ukrainian and Arabic have
plural categories English does not; a non-plural key leaves their translators
nowhere to put them, and retrofitting one means re-translating. i18next picks
the suffix from the active language's CLDR rules, so a translator adding
`count_few` / `count_many` needs no code change.

The rule runs in the other direction as well: a locale writes **its own**
categories, not English's. Chinese has one (`other`), so `zh` carries a single
`_other` key per plural family and no `_one` — a mirrored `_one` would be an
entry i18next could never select. A locale's key count is expected to differ
from `en`'s for exactly this reason; parity is per plural *family*, not per
key.

## RTL

`languages.ts` carries a `dir` per language and `index.ts` writes it to
`<html dir>` on every change. No RTL locale ships yet; the plumbing is in place
so adding one is a catalogue change rather than a layout change.

## Not translated

Console output, `Error` values destined for logs, `data-testid` values,
developer-facing/debug strings, and protocol or preference key names.

## Tests

`e2e/i18n.spec.ts` (browser tier, both skins) covers: the selector renders and
persists across reload; switching language changes rendered copy; and a key
missing from a non-English catalogue falls back to English rather than
rendering the raw key. It seeds a synthetic test locale through the same
`__POLLIS_PRELOAD__` mock the other specs use, so the assertions do not depend
on which real locales happen to ship.
